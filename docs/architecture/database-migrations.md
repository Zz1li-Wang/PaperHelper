# Database migration policy

Paper Helper uses one forward-only Alembic revision chain for its authoritative
PostgreSQL database. The chain remains empty until the first ORM model is added.

## Developer workflow

Run commands from the repository root:

```bash
make migration-heads
make migration-revision m=add_workspace
make migration-upgrade
make migration-check
```

`PAPER_HELPER_DATABASE_URL` must contain an explicit SQLAlchemy asyncpg URL.
Alembic never creates the target database and application processes never run
migrations during startup.

Every autogenerated revision must be reviewed for table ownership, constraint
names, indexes, server defaults, locking behavior, and data-loss risk. Do not
edit a revision after it has been merged. Correct released migrations with a new
forward revision.

## Revision graph

Zero heads are allowed only while `backend/migrations/versions/` contains no
revision files. After the first revision, the graph must have exactly one head.
When parallel branches introduce multiple heads, resolve them explicitly:

```bash
make migration-merge m=merge_parallel_heads
```

A merge revision only joins the graph. It does not resolve conflicting DDL or
business semantics, so the combined migration path still requires review and a
fresh-database CI run.

## Compatibility and data changes

Production changes use expand/contract across compatible application releases:

1. Add backward-compatible structures.
2. Deploy code that can use both old and new structures.
3. Backfill data with bounded, observable work.
4. Enforce new constraints and remove old structures in a later release.

Revision files must be self-contained. They may use Alembic, SQLAlchemy Core,
and constants frozen in the revision, but must not import mutable application
models, enums, services, or initializers. Large or externally visible backfills
belong in separately operated jobs rather than a schema migration transaction.

Downgrades are not the production rollback mechanism. Roll back to a compatible
application version when possible, then ship a corrective forward revision.

## CI and deployment

The required `Database / migrations` check runs against a fresh PostgreSQL 16
database, upgrades the full chain twice, and runs `alembic check` to detect ORM
drift. It never connects to shared test, staging, or production databases.

Deployment must execute `alembic upgrade head` once as a dedicated pre-start
task. Web API, MCP Server, Agent Worker, and Ingestion Worker start only after
that task succeeds.
